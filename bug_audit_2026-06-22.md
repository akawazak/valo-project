# ValoVault — Full Bug Audit & Permanent Fix Plan

> Companion to `bug_investigation.md` (which already lists 5 bugs that were
> filed in `valovault/bug_investigation.md` on 2026-05-31). This report
> extends the audit to every layer of the app and proposes a permanent,
> root-cause fix for each finding — not just a patch.

Bugs are grouped by **severity**:

- **P0** — App can crash, lose user data, or be stuck in a permanent bad state.
- **P1** — Visible breakage users hit daily (silent 401s, wrong rank, etc.).
- **P2** — Latent bugs that surface under specific user / timing patterns.
- **P3** — Code quality / hygiene that will cause bugs in the future.

Each entry has:
1. **Symptom** — what the user sees.
2. **Root cause** — the exact line(s) of offending code.
3. **Permanent fix** — code-level change with rationale.
4. **Verify** — how to confirm it's actually fixed.

## P0 — Data loss / app stuck

### B-01 · `settings.Get()` silently swallows read errors and re-emits defaults

**File:** `backend/settings/settings.go:24-35`

```go
func Get() (*Settings, error) {
    data, err := GetRaw()
    if err != nil {
    }                                   // ← empty branch — err is dropped
    settings := new(Settings)
    if err := json.Unmarshal(data, settings); err != nil {
        return nil, err
    }
    return settings, nil
}
```

**Symptom**
First launch (or any time the file is missing / unreadable), `GetRaw()` already
returns the JSON for `DefaultSettings` (which has `AutoSelectAgent: true`).
That JSON gets *unmarshalled* into a fresh `Settings` and the in-memory copy
**overrides whatever the user has persisted** as soon as the next `Save` runs.
On Windows, this is also why `getSettings` round-trips even when the file is
unreadable (e.g. AV scan hold).

**Permanent fix**

```go
func Get() (*Settings, error) {
    data, err := GetRaw()
    if err != nil {
        return nil, err                 // propagate real I/O errors
    }
    s := new(Settings)
    if err := json.Unmarshal(data, s); err != nil {
        return nil, err
    }
    return s, nil
}
```

If we want to keep the "missing-file returns defaults" behaviour, do it in
`GetRaw` only, and stop re-`Unmarshal`ing defaults on every call.

**Verify**
`go test ./backend/settings/...` after adding a `TestGetMissingFile` and
`TestGetCorruptFile` case (see patch in `Patches/`).

### B-02 · `usePresets.refreshFromGame` discards in-progress edits on read failure

**File:** `frontend/src/hooks/usePresets.ts:108-128`

```ts
const refreshFromGame = useCallback(async () => {
    try {
        const playerData = await getPlayerLoadoutData();
        setGameLoadout(playerData.loadout);
        setGameMeta({ sprays: playerData.sprays, identity: playerData.identity });
        if (!isEditingRef.current) { ... }
        return playerData;
    } catch (error) {
        onPresetSelectError(error);
        throw error;            // re-throw, but no recovery
    }
}, [onPresetSelectError]);
```

**Symptom** — Any transient fetch failure mid-edit (network blip, backend
restart) calls `onPresetSelectError`, which opens the `ErrorModal` in
`page.tsx`. The user's unsaved edits are *not* rolled back, but the next
`useEffect` re-render can still overwrite the snapshot because `isEditingRef`
is the only guard. Combined with the parent's `loadInitialData` on puuid
change, the user can lose work.

**Permanent fix**
- Don't propagate *read* failures as errors to the user during edit mode.
- Use a snapshot rollback ONLY on `POST /v1/apply-loadout` (the actual write).
- Centralise "current edits" in a ref so the effect that overwrites them
  cannot race with `refreshFromGame`.

```ts
const refreshFromGame = useCallback(async () => {
    try {
        const playerData = await getPlayerLoadoutData();
        setGameLoadout(playerData.loadout);
        setGameMeta({ sprays: playerData.sprays, identity: playerData.identity });
        if (!isEditingRef.current) {
            setSelectedPreset({ ...defaultPreset, loadout: playerData.loadout });
            setCurrentLoadout(playerData.loadout);
        }
        return playerData;
    } catch (error) {
        // Soft-fail: do NOT surface to user. Game state stays stale.
        console.warn('refreshFromGame failed; keeping previous game state', error);
        return null;
    }
}, []);
```

**Verify**
While editing a preset, stop the backend (`Ctrl-C` on `go run .`). The
`ArsenalView` should keep showing the editing snapshot; the "Apply" button
should still be clickable; no modal should pop.

### B-03 · `cancelAccountRefresh` is a no-op if no refresh is in flight, and the UI never reflects the cancel state

**File:** `frontend/src/context/DataContext.tsx:605-611`, `frontend/src/components/AccountManagerModal.tsx:31-76`

**Symptom** — User clicks "✕" on the cancel-refresh button. The handler calls
`onCancelRefresh(acc)` which calls `refreshCancelRef.current.get(sessionKey)`.
If the refresh finished between the moment the button was rendered and the
click, the cancel handle is gone, the click does nothing, and the row stays
in "refreshing" state until the next successful `setRefreshingPuuids(prev => ({...prev, [puuid]: false}))` fires from a DIFFERENT refresh's finally.

**Permanent fix**
After the click, optimistically mark the row as not-refreshing; rely on the
in-flight promise to re-mark it if needed:

```ts
const handleCancelRefresh = (e, acc) => {
    e.stopPropagation();
    setRefreshingPuuids(prev => ({ ...prev, [acc.puuid]: false }));
    onCancelRefresh(acc);
};
```

In `DataContext.refreshAccountToken`, the cancel function is registered only
*after* `releaseLock` can no longer fire from outside, so we also need to
make `cancel` a no-op after `releaseLock`. Add an idempotent guard:

```ts
const cancel = () => {
    if (resolved) return;          // already finished
    finish(false);
    invoke('close_login_window', { sessionId }).catch(() => {});
};
```

**Verify**
Spam-click the cancel button on a row that just finished refreshing.
The UI should always settle in a non-refreshing state within one tick.

### B-04 · Tauri WebView2 `data_directory` race on rapid re-open

**File:** `frontend/src-tauri/src/lib.rs:62-68`

```rust
if let Some(window) = app_handle.get_webview_window(&window_label) {
    let_ = window.close();
}
std::thread::sleep(std::time::Duration::from_millis(50));   // ← race-prone
```

**Symptom** — `open_login_window` is called from React with the same
`sessionId` in quick succession (e.g. user clicks ↻ Refresh on a different
account, then the in-flight redirect fires). Tauri schedules destruction
asynchronously. 50 ms is not always enough on a busy machine, so the
second `WebviewWindowBuilder::build` fails with "label already exists",
returning an error to JS. The login UI then hangs with "Refreshing…"
because the `refreshAccountToken` promise never resolves.

**Permanent fix**
Use Tauri's `on_window_event(Destroyed)` or wait for the
`WindowEvent::Destroyed` event before re-building, OR dedupe in JS. The
simplest cross-platform fix is a per-label async mutex:

```rust
use tokio::sync::Mutex;
use std::collections::HashMap;
use std::sync::Arc;

type WindowLockMap = Arc<Mutex<HashMap<String, Arc<Mutex<()>>>>>;

#[tauri::command]
async fn open_login_window(...) -> Result<(), String> {
    let _guard = acquire_window_lock(state, &window_label).await;
    // … close + sleep + build …
    Ok(())
}
```

The `acquire_window_lock` helper serialises calls for the same label and
releases after the WebView is built, guaranteeing a clean rebuild.

**Verify**
Test scenario: with a refresh in flight for account A, click ↻ on account B
within 100 ms. The new window must open cleanly.

### B-06 · `applyLiveMMRToOverview` clobbers `CurrentRank.RankedRating` from cache with `comp.RankedRating` even when comp is 0

**File:** `backend/handlers/profile.go:152-177`

```go
if comp.RankedRating > 0 {
    overview.CurrentRank.RankedRating = comp.RankedRating
}
if comp.CurrentSeasonGamesPlayed > 0 {
    overview.CurrentRank.NumberOfGames = comp.CurrentSeasonGamesPlayed
}
```

**Symptom** — User with no games this act (PlacementState hidden by Riot
because they haven't placed yet) loses the cached RR from last act because
`comp.RankedRating` is 0 and we *skip* the write, but THEN the seasonal
fallback block (`if season, ok := comp.SeasonalInfoBySeasonID[seasonID]; ok
{ ... season.RankedRating ... }`) overwrites again only if `seasonID` is set.
If the user has no live season at all, the cached `overview.CurrentRank.RankedRating`
stays correct, but if they have a seasonal entry with `RankedRating: 0` (e.g. just
reset after episode), the function sets it to 0.

**Permanent fix** — Only write the seasonal value when it would not zero out
a non-zero existing value, AND only when the seasonal season is the *current*
season:

```go
if season, ok := comp.SeasonalInfoBySeasonID[seasonID]; ok {
    if season.NumberOfGames > 0 {
        overview.CurrentRank.NumberOfGames = season.NumberOfGames
    }
    if season.TotalWins > 0 {
        overview.CurrentRank.NumberOfWins = season.TotalWins
    }
    // Only overwrite RR if the season says we have a real value.
    if season.RankedRating > 0 {
        overview.CurrentRank.RankedRating = season.RankedRating
    }
    ...
}
```

This was already partly done in the live branch; the fix is to also gate
the seasonal branch by `season.RankedRating > 0`.

**Verify**
Add a test: cached `RankedRating=84`, live season `RankedRating=0`. Result
should keep `84` (not 0).

### B-07 · `GetOverview` season-summary uses the *wrong* table for top agent

**File:** `backend/tracking/db.go:941-952`

```go
row = db.QueryRow(`
    SELECT characterId
    FROM agent_stats
    WHERE puuid = ? AND queue = 'all'
    ORDER BY matches DESC, characterId ASC
    LIMIT 1
`, puuid)
```

**Symptom** — `agent_stats.queue = 'all'` is a valid row, but if a user has
played zero matches in any queue, `agent_stats` is empty, and this `QueryRow`
returns `sql.ErrNoRows` which is silently swallowed. Top agent stays empty.
This is correct behaviour for "no data yet" but **inaccurate** for "I have
data but only in non-default queues" because `RecomputeAggregates` always
populates `queue='all'` by summing over queues. Verified OK in the code;
real bug is **the count `NumberOfGames` is set BEFORE the
`recompute_aggregates` filter on Competitive**:

Look at line 937:
```go
out.CurrentRank.NumberOfGames = matches   // ← total matches across ALL queues
out.CurrentRank.NumberOfWins = wins
```

But the front-end displays these as "Competitive" games. So a user who plays
only Swiftplay shows 20/0/0% WR on the **Competitive** card.

**Permanent fix**
`GetOverview` needs to optionally take a `queue` filter and only sum matches
with `m.queueID = 'competitive'`. Or add a new `currentRankNumberOfGames`
field that comes from the live MMR (which is correct). The cleanest fix:

```go
// Only count ranked (competitive) matches in the displayed counter
err = db.QueryRow(`
    SELECT COUNT(*),
           COALESCE(SUM(CASE WHEN (m.blueWins=1 AND mp.teamId='Blue')
                             OR (m.blueWins=0 AND mp.teamId='Red')
                        THEN 1 ELSE 0 END), 0)
    FROM matches m JOIN match_players mp ON mp.matchID = m.matchID
    WHERE mp.subject = ? AND m.isRanked = 1
`, puuid).Scan(&matches, &wins)
```

**Verify**
User with 5 competitive + 15 swiftplay matches shows "5 games" in the rank
card (not 20).

### B-08 · `GetRRSnapshots` and `ListCachedMatches` join via `rr_snapshots.puuid` but the front-end `ProfilePanel` displays stale snapshots because the new `puuid` column in `rr_snapshots` was only just added — old rows from before the migration are dropped

**File:** `backend/tracking/db.go:150-183` (`migrateRRSnapshotsTable`)

```go
if hasTable && !hasPuuid {
    if _, err := db.Exec("DROP TABLE rr_snapshots"); err != nil {
        return fmt.Errorf("drop legacy rr_snapshots: %w", err)
    }
}
```

**Symptom** — Existing users with competitive history lose ALL their RR
graph the first time they upgrade to this build. The migration is
intentionally destructive because the old schema had no `puuid` and thus
couldn't be safely re-keyed.

**Permanent fix** — Three options, in order of preference:

1. **Migrate in-place**: add a `puuid` column with the player's PUUID by
   inferring it from `match_players` (the only place a `puuid` is recorded
   per match) before dropping:

```sql
ALTER TABLE rr_snapshots ADD COLUMN puuid TEXT NOT NULL DEFAULT '';
UPDATE rr_snapshots
   SET puuid = (SELECT mp.subject FROM match_players mp
                 WHERE mp.matchID = rr_snapshots.matchID LIMIT 1)
 WHERE puuid = '';
```

Then re-key the PK:
```sql
-- Save off the data, drop, recreate, reinsert. SQLite ALTER TABLE can't
-- drop a PK column, so this requires the same drop/recreate dance but
-- preserves the rows.
```

2. **Add a re-migration tool** that runs once and warns the user.
3. **Document the data loss in the release notes** (worst — users complain).

This is the single highest-value fix in the whole audit: it directly
addresses the "my RR graph is empty after update" complaint.

**Verify**
Run on a pre-migration DB (any DB created before this commit). After
restart, `GetRRSnapshots` should return the old rows with the inferred
`puuid`.

### B-10 · `GetLiveMatch` (coregame) has a data race: goroutines write to `resp.AllyTeam[index]` without synchronisation

**File:** `backend/handlers/livematch.go:163-202`

```go
for i := range match.AllyTeam.Players {
    wg.Add(1)
    go func(index int) {
        defer wg.Done()
        ...
        resp.AllyTeam[index] = lp        // ← UNSYNCHRONISED
    }(i)
}
```

The `EnemyTeam` block has the same issue (line 229). The `coregame` block
below (line 304) correctly uses a mutex.

**Symptom** — `go test -race` flags the write. In production, a slice
element write is technically safe (each goroutine writes a different index)
but the *reads* of `resp` (after `wg.Wait()`) may observe partially-written
state if the slice header is reallocated by another goroutine. More
important: the `LiveMatch` endpoint occasionally returns a player with
`nil` because the array slot wasn't yet assigned when the JSON encoder
walks it.

**Permanent fix** — mirror the coregame pattern:

```go
var wg sync.WaitGroup
var mu sync.Mutex
resp.AllyTeam = make([]*LivePlayer, len(match.AllyTeam.Players))
for i := range match.AllyTeam.Players {
    wg.Add(1)
    go func(index int) {
        defer wg.Done()
        lp := buildLivePlayer(...)
        mu.Lock()
        resp.AllyTeam[index] = lp
        mu.Unlock()
    }(i)
}
```

Or simpler: collect into a local `[]*LivePlayer` and assign after `wg.Wait()`.

**Verify**
`go test -race ./backend/handlers/...` is clean. Smoke-test: open the
pregame overlay 5 times; all players must always appear.

### B-12 · `useLoadout.handleApplyLoadout` shows "Successfully applied" toast on a backend 4xx (because `applyLoadout` throws only on non-OK status, but the back-end writes `500` for *any* `returnError`)

**File:** `backend/handlers/handlers.go:468-471` and `frontend/src/hooks/useLoadout.ts:11-26`

**Symptom** — If the local Valorant client closes mid-apply, the Go handler
returns `500` with body `"an error occurred: ..."`. The fetch returns `response.ok = false`,
`applyLoadout` throws, so the toast does NOT show. **But** if the body is empty (the
`returnAny` path on success can write nothing when the response is `nil`), the body
parser may succeed and return `undefined`, so the success toast shows for a
no-op. Two-sided bug.

**Permanent fix (backend)** — always write a JSON envelope with status:

```go
func (h *Handler) returnError(w http.ResponseWriter, err error) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusInternalServerError)
    _ = json.NewEncoder(w).Encode(map[string]any{
        "ok":    false,
        "error": err.Error(),
    })
}
func (h *Handler) returnAny(w http.ResponseWriter, response any) {
    payload, _ := json.Marshal(map[string]any{"ok": true, "data": response})
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK)
    w.Write(payload)
}
```

**Permanent fix (frontend)** — `applyLoadout` in `api.ts` should assert
`response.ok` AND the `ok` field of the JSON body:

```ts
const data = await response.json().catch(() => ({}));
if (!response.ok || data?.ok === false) {
    throw new Error(data?.error || 'Failed to apply loadout.');
}
```

**Verify**
Apply loadout with the local client closed → ErrorModal opens. Apply with
the client open → Toast shows "Successfully applied …".

### B-13 · `Tick.Stop` panics if called before `Start`

**File:** `backend/tick/tick.go:198-205`

```go
func (t *Ticker) Stop() {
    if !t.running {
        return
    }
    close(t.stopCh)        // ← panics if channel was already closed elsewhere
    t.running = false
}
```

**Symptom** — `handlers.go:RestartTicker` is now removed (good), but the
updater / app shutdown path can call `Stop` twice. `close` on an
already-closed channel panics → backend crash → 502s on every endpoint.

**Permanent fix** — use `sync.Once` for the close, OR `recover` in the
caller. The cleanest:

```go
import "sync"

type Ticker struct {
    Val     *valclient.ValClient
    stopCh  chan struct{}
    stopOnce sync.Once
    runningMu sync.Mutex
    running bool
}

func (t *Ticker) Stop() {
    t.runningMu.Lock()
    defer t.runningMu.Unlock()
    if !t.running {
        return
    }
    t.stopOnce.Do(func() { close(t.stopCh) })
    t.running = false
}
```

**Verify**
Call `Stop()` twice in a row in a unit test. No panic.

### B-14 · `tick.Start` ignores the agent-lock state and applies a preset *while* the user is mid-pick (selection not yet locked)

**File:** `backend/tick/tick.go:96-114`

```go
for _, mp := range match.AllyTeam.Players {
    if mp.Subject != player.Subject {
        continue
    }
    if mp.CharacterSelectionState == valclient.CharacterSelectionStateLocked {
        locked = true
    }
    agentUuid = mp.CharacterID
    continue
}

if locked {
    continue          // ← only blocks if THE LOCAL PLAYER is locked
}
```

**Symptom** — The intent is "don't apply if I'm already locked in", but the
filter only checks `mp.CharacterSelectionState == Locked`. There's a
**Pending** state (locked but not finalised) and a **Selected** state that
Riot uses for "user has picked, waiting on others". If the local player
has Selected but not yet Locked, the code applies the preset **over their
pick**, which is exactly the "why did my agent change?" bug.

**Permanent fix**

```go
if mp.CharacterSelectionState == valclient.CharacterSelectionStateLocked ||
   mp.CharacterSelectionState == valclient.CharacterSelectionStateSelected {
    locked = true
}
```

OR (more correct): only apply when ALL teammates have locked, so the
local player's pick is final and teammates have committed.

**Verify**
Pick an agent in the live game; with the local agent in the "Selected" state
(yellow tick visible), the auto-apply must NOT fire.

### B-17 · `RiotLoginCard.handleStartLogin` overwrites `currentSessionIdRef.current` with a *random* id, but `connectWithUrl` later calls `persist_login_session(fromSessionId=temp, toSessionId=stable)`. If the user starts login again before the first one finishes, the temp session is reused and the persisted session is wrong.

**File:** `frontend/src/components/RiotLoginCard.tsx:184-200`, `frontend/src-tauri/src/lib.rs:196-226`

**Symptom** — User opens the login window for account A, leaves it open,
opens login for account B. Account A's first redirect may have its
cookies saved under B's session, because the temp sessionId is shared
in the global ref. After the first `persist_login_session`, account A's
cookie directory is destroyed.

**Permanent fix** — store the temp session ID in component state, not a
module-level ref, and gate the second `handleStartLogin` on
`currentSessionIdRef.current === ""` (a "no refresh in flight" sentinel):

```ts
const [activeSession, setActiveSession] = useState<string | null>(null);
async function handleStartLogin() {
    if (activeSession) return;       // one at a time per card
    const temp = `session_${Date.now()}_...`;
    setActiveSession(temp);
    ...
    await connectWithUrl(...);
    setActiveSession(null);
```

### B-19 · `RiotLoginCard.activateAccount` always overwrites `riot_access_token` even when the account has empty tokens (e.g. the local-client-only flow)

**File:** `frontend/src/components/RiotLoginCard.tsx:235-246`

```ts

    puuid: localAccount.puuid,
    accessToken: "",                     // ← empty
```

*active* account has this flag.

**Verify**

### B-24 · `lib.rs` redirect handler has wrong operator precedence (silent functional bug)

**File:** `frontend/src-tauri/src/lib.rs:111-144`


Per Rust operator precedence, this parses as:
```rust
if host == "localhost" || (host == "127.0.0.1" && path == "/redirect") {
```

So if `host == "localhost"` and `path` is anything (e.g. `/favicon.ico`),

`http://localhost/redirect#access_token=...`, so the bug only surfaces
on misclicks. **P2.**

**Permanent fix**

```rust
if (host == "localhost" || host == "127.0.0.1") && path == "/redirect" {
```
